**ハク**: タクさん！最近「Cursor」とか「MCP（Model Context Protocol）」って言葉をよく聞くんですけど、AIってただコードを自動生成してくれるだけのツールじゃないんですか？

**タク**: いいところに気がついたね、ハク。これまでは「コードの自動補完」がメインだったけど、今はAIが自律的にコンテキストを理解してツールと連携するフェーズに入っているんだ。海外では「Crime Pays but Botany Doesn't（派手な機能開発は評価されるが、地味な基盤メンテは放置されがち）」なんて言われたりするけど、この「地味な作業」をAIに任せるのが今のトレンドだよ。

**ハク**: 地味な作業……つまり、型定義のメンテナンスとか、CI/CDのエラーチェックとかですか？確かにそういうのって後回しにしちゃって、後から巨大な技術負債になったりしますよね。でも、具体的にどうやってMCPがそれを解決してくれるんですか？

**タク**: そこで重要になるのが「Discovery Loop（発見のループ）」の高速化だ。従来の開発では、フロントエンドのエラーとインフラのログが分断されていたりして、原因究明に時間がかかっていた。MCPを使うと、CursorのようなAIエディタから直接インフラログや最新のスキーマにアクセスして、AIに課題を発見・解決させることができるんだよ。

**ハク**: なるほど！エディタが直接色んなツールと喋れるようになるってことですね。でも、実際のアーキテクチャってどうなってるんですか？既存の仕組みとどう違うのか気になります。

**タク**: いい質問だ。簡単に言うと、Cursorと各種ツールをMCPというプロトコルで繋ぐんだ。具体的な構成とメリットをまとめた表を見てみよう。

| 連携ツール (MCP経由) | 取得するコンテキスト | 解決できる課題 (Discovery Loopへの貢献) |
| :--- | :--- | :--- |
| OpenAPI / Supabase | 最新の型定義・データベーススキーマ | バックエンドとの型不整合を即座に検知し、フロントの実装を自動修正 |
| Sentry / Datadog | リアルタイムのエラーログ | 本番環境のエラーログから、該当するソースコードを特定して修正案を提示 |
| GitHub / CI | パイプラインの状態・変更履歴 | デプロイ失敗時に、どの環境変数の変更が原因かを特定して `.env` を修正 |

**ハク**: おおー、これなら「フロントエンド側で環境変数が足りなくてビルドが落ちた」みたいな地雷も即座に回避できそうですね！でも、実務で使う上で気をつけないといけない落とし穴（地雷）ってないんですか？

**タク**: もちろんあるよ。よくあるアンチパターンとその対策をいくつか紹介しよう。

*   **地雷1: AIのハルシネーション（嘘コード）によるサイレントブレイク**
    *   **原因**: エディタが古い型定義やドキュメントしか持っていない状態でAIにコードを書かせてしまう。
    *   **対策**: MCP経由で「最新のビルド結果」や「型チェック結果（`tsc --noEmit` など）」をリアルタイムでAIに読み込ませ、ツール実行のループ内で検証させる。
*   **地雷2: インフラとフロントエンドの連携漏れ（環境変数のズレ）**
    *   **原因**: DevOps側で追加された環境変数がフロントの型定義（`env.mjs` など）に反映されていない。
    *   **対策**: CIツールとMCPで繋ぎ、エラー時にログを解析させて即座にZodなどのバリデーションスキーマを修正させる。

**ハク**: 情報をAIに与えっぱなしにするんじゃなくて、常に最新の「結果」をフィードバックするループを作ることが大事なんですね！

**タク**: その通り。最先端のAIモデルは「ただコードを書かせるツール」ではなく、「文脈を繋ぎ、ループを回す相棒」としてアーキテクチャに組み込むべきだ。地味な基盤整備を自動化すれば、チーム全体の開発速度と品質が飛躍的に上がるからね。

**ハク**: よーし、僕もまずはローカルのプロジェクトにMCPサーバーを立てて、型チェックの自動フィードバックループを作ってみます！
