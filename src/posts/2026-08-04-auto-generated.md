description: "AIエージェントの基盤となるModel Context Protocol (MCP) において、ステートレス設計が再び脚光を浴びている理由とそのメリットについて考察します。"
---

**ハク**: Hacker Newsで「Stateless MCP has recaptured my interest」というトピックが話題に上がっています。Model Context Protocol (MCP) は元々ステートフルなエージェントワークフローを想定して構築された側面が強いですが、ここに来てなぜステートレス設計に回帰しているのでしょうか。

**タク**: 理由は主に3つに集約されます。コンテキストウィンドウの拡大、アーキテクチャの複雑性排除、既存インフラとの親和性です。

* **コンテキストウィンドウの拡大**: LLMが100万トークン以上のコンテキストを扱えるようになり、状態を外部保存するトークン節約の意義が薄れました。毎回必要な情報を全てリクエストに含める力技が効率的になっています。
* **複雑性の排除**: ステートフルなサーバーはセッション管理やメモリ同期などの認知負債を引き起こします。ステートレス化によりリクエストとレスポンスが完全に分離し、デバッグとスケーリングが容易になります。
* **既存インフラとの親和性**: ステートレス設計は既存のHTTP/RESTベースのマイクロサービスや、AWS Lambdaのようなサーバーレスアーキテクチャとそのまま統合可能です。

**ハク**: その「毎回必要な情報を全てリクエストに含める」というアプローチですが、レイテンシの増大や、トークン処理にかかるAPIコストの増加という明確なデメリットが存在するはずです。これらに対する現在の解決策やトレードオフの落とし所はどうなっているのでしょうか。

**タク**: 指摘の通り、レイテンシとコストは主要なトレードオフです。現在の解決策は以下の技術的アプローチによって緩和されています。

* **プロンプトキャッシングの普及**: 主要なLLMプロバイダがキャッシュ機能を提供し、同一または類似の巨大なコンテキストを再送信した際のコストとレイテンシを大幅に削減しています。
* **チャンク化と遅延ロード**: すべてを一度に送るのではなく、インデックス情報だけを先に送り、詳細が必要になったタイミングでMCPツールを呼び出してオンデマンドで取得する設計が一般化しています。
* **エッジコンピューティング**: ステートレスMCPサーバー自体をCloudflare Workersなどのエッジに配置し、ツール実行自体のネットワークレイテンシを極限まで削る構成が採用されています。

**ハク**: キャッシュとオンデマンド取得の組み合わせでコストを抑えつつ、インフラ側でレイテンシを相殺しているという構造ですね。では、既存のステートフルなアプローチとステートレスMCPの適用領域の違いをどのように定義すべきでしょうか。

**タク**: ユースケースに応じた明確な境界線が存在します。以下の表で整理します。

| 比較項目 | ステートレスMCP | ステートフルMCP (従来型エージェント) |
| :--- | :--- | :--- |
| **主な用途** | 単発のタスク実行、インフラ連携、データ取得 | 長期の計画策定、複雑な自律型ワークフロー、対話型セッション |
| **状態の保持場所** | LLMのコンテキストウィンドウ、またはクライアント側 | MCPサーバー、または外部データベース (Vector DBなど) |
| **スケーリング** | リクエスト単位で容易に水平スケール可能 | セッションの維持が必要でスケールに工夫が必要 |
| **デバッグの容易さ** | 入出力が決定論的であり極めて容易 | 状態の依存関係があるため再現性が低く困難 |

インフラレベルのツール連携においては、予測可能でスケールしやすいステートレスMCPが標準的なデザインパターンとして定着していくと予想されます。
